Article 3 · 脚手架设计

环境工程：特性列表、Git与进度追踪

JSON vs Markdown、passes字段语义、Git的双向价值——三个组件解决三个问题

一、三个组件，三个问题

组件解决的问题本质
特性列表目标模糊：Agent不知道"做完"是什么意思"什么是完整"的唯一定义
Git工作流状态污染：环境在会话间退化代码质量的版本锚点
进度文件记忆断层：新Agent不知道之前发生了什么Agent间的交接文档

二、特性列表：完整性的唯一定义

"We prompted the initializer agent to write a comprehensive file of feature requirements expanding on the user's initial prompt. In the claude.ai clone example, this meant over 200 features."

初始化Agent基于用户的简短prompt展开出一份详尽的特性需求文件，每个特性条目具有以下结构：

  • category：分类标记，用于优先级排序和分组
  • description：面向人类的特性描述，简洁明了
  • steps：可执行的具体验证步骤——不是抽象需求，而是可操作的测试脚本
  • passes：唯一的可变状态，所有特性初始为false

JSON vs Markdown：格式选择的教训

"After some experimentation, we landed on using JSON for this, as the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files."

Agent在处理Markdown文件时有倾向去"重写"或"润色"其内容——这是语言模型在文本生成任务上的天性。而JSON的结构化特性使得Agent更倾向于只修改特定字段（如passes），而非重写整个文件。

三、Git工作流：代码质量的版本锚点

Git在长运行Agent场景中承担了双重角色：

  • 回溯工具：Agent犯错时，git revert让后续Agent能够一键回到上一个已知的干净状态
  • 交接工具：git log --oneline -20让下一个Agent瞬间看到"最近20个会话做了什么"

四、四核心设计原则

  1. 不可变优于可变——特性列表的字段结构是不可变的，Agent只能改passes字段
  2. 默认否定优于默认肯定——所有特性初始为passes:false，"有罪推定"
  3. 人类工具优于专用系统——Git、文本文件、JSON，不依赖任何特定的Agent框架
  4. 结构化优于非结构化——JSON让Agent的行为更容易被约束
"Inspiration for these practices came from knowing what effective software engineers do every day."
