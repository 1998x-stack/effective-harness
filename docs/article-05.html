二、开放问题一：单Agent还是多Agent？

"It's still unclear whether a single, general-purpose coding agent performs best, or if better performance can be achieved through a multi-agent architecture."

原文提出了一个自然的推演方向——按软件开发生命周期中的角色进行Agent专业化：

  • 测试Agent——专注于端到端测试、边界条件、回归验证
  • 质量保证Agent——检查代码风格、性能、安全、架构一致性
  • 代码清理Agent——消除技术债务、统一代码风格

但多Agent架构有隐性成本：协调开销、状态一致性、故障传播、调试复杂度。两Agent方案的优雅之处正在于它刚好够用——任何向多Agent架构的跃迁，都必须用实验数据证明收益超过这些新增成本。

三、开放问题二：从Web开发到通用领域

"This demo is optimized for full-stack web app development. A future direction is to generalize these findings to other fields — for example, scientific research or financial modeling."

科学研究和金融建模各有独特挑战：目标可能随实验结果漂移、测试反馈回路可能长达数天、代码与结果的关系可能是非确定性的。但核心方法论是可以迁移的。

四、六条可迁移设计原则

  1. 记忆外化——把状态从Agent的上下文窗口外化到文件系统中
  2. 不可变规约——Agent的行为边界必须由不可变的规约定义
  3. 增量契约——每个Agent会话必须在结束时留下定义良好的完成状态
  4. 验证优先于推进——每次会话的第一个动作不是向前推进，而是向后验证
  5. 人类工具即Agent工具——不要为Agent发明新的基础设施
  6. 简单至上——在实证数据证明收益之前，不要增加复杂度

五、结语

"This work reflects the collective efforts of several teams across Anthropic who made it possible for Claude to safely do long-horizon autonomous software engineering."

Anthropic的博文不是一篇发布完美解决方案的论文，而是一份来自前线的工程笔记。它最有价值的部分不是具体的JSON格式或Puppeteer配置，而是它展示的方法论态度：从观察失败模式开始，从人类工程师的日常实践中提取灵感，保持方案极简，坦诚标记开放问题。
