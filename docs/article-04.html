Article 4 · 测试与验证

测试驱动Agent：浏览器自动化与E2E验证

Puppeteer MCP闭环、启动序列三阶段、截图验证回路——给Agent装上一双眼睛

一、测试：长运行Agent最隐蔽的失败模式

"One final major failure mode was Claude's tendency to mark a feature as complete without proper testing. Claude tended to make code changes, and even do testing with unit tests, but would fail to recognize that the feature didn't work end-to-end."

Agent会做出代码变更、运行单元测试，但测试通过了就认为特性完成了——即使端到端流程根本不工作。这是一个"局部正确但全局错误"的典型案例。

二、Puppeteer MCP：给Agent装上一双眼睛

"Claude mostly did well at verifying features end-to-end once explicitly prompted to use browser automation tools and do all testing as a human user would."

关键变化发生在两个维度上：工具层面（浏览器自动化）和Prompt层面（像人类用户一样测试）。在架构上制造了一个闭环：

Agent编写代码 → 重启开发服务器 → Puppeteer打开浏览器 → 执行用户操作 → 截图反馈 → Agent判断结果

三、会话启动中的测试协议

每个编码Agent打开会话后，第一件事不是开始写代码，而是跑一遍冒烟测试：

  1. 启动开发服务器（通过init.sh）
  2. 用Puppeteer打开应用
  3. 执行一个完整的核心流程
  4. 确认核心功能正常
"If the agent had instead started implementing a new feature, it would likely make the problem worse."

如果Agent跳过测试直接开发新特性，它可能在一个已经被破坏的基础上继续堆代码——让问题雪上加霜。

四、标准会话启动序列

阶段步骤目的
定位pwd → progress.txt → feature_list.json → git log理解当前状态
验证init.sh → 启动服务器 → 端到端测试确认环境干净
行动选定特性 → 实现 → 测试 → Commit → 更新进度增量推进

五、工具局限

"Some issues remain, like limitations to Claude's vision and to browser automation tools. For example, Claude can't see browser-native alert modals through the Puppeteer MCP."

浏览器原生模态框不可见、视觉模型精度有限、时序问题难捕获——这些都是实际的工程限制，但自动化测试工具在当前水平上已经能捕获80%以上的bug。

六、三层测试方法

  1. 自动化回归（init.sh冒烟测试）——每次会话启动时执行
  2. 特性验证（Puppeteer端到端测试）——每个特性实现后执行
  3. 视觉确认（截图回路）——Agent查看浏览器截图，判断视觉呈现
